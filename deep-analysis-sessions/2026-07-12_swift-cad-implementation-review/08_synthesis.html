先に、3つの回答

評価対象を「公式の狭いパイプライン」と「戦略ゴール」に分けると、結論は明確です。

NO — BROAD GOAL

機能は十分か

矩形押し出しを中心とするサブセットには実体があります。一方、一般制約、一般 Boolean、fillet / shell / patch、pattern、技術図面、exact CAD 交換は未完成です。さらに単独 package 解決と CI が停止しています。

MIXED

要件は妥当か

source-of-truth、単位、tolerance、決定性、fail-closed は妥当です。ただし現行サポート、実装状況、ロードマップが混在し、受入契約としては一意・追跡可能ではありません。

YES — MATERIAL

ゴールは過小評価されたか

はい。過小評価されたのは機能数より「1機能を製品化する深さ」です。堅牢幾何、命名、API parity、schema migration、conformance、性能、運用証拠が横断ゲートになっていません。

07 / 08

推奨する回復順序

新機能追加を止めること自体が目的ではありません。次の追加が「完成した能力」になる順序です。

GATE 0

Build truth

remote dependency を成立させ、clean macOS / WASM CI を green にし、source-rule check の誤検出を除く。

Exit: fresh consumer fixture + current CI green
GATE 1

Contract truth

現行 support と roadmap を分離し、能力 ID、入力 geometry、unsupported code、parity、受入証拠を1つの ledger にする。

Exit: public capability → requirement → test の traversal が可能
GATE 2

Compatibility truth

schema version を実態に合わせ、migration、historical fixture、API diff、deprecated lifecycle を導入する。

Exit: 旧 native file と前 release client の互換性を CI で証明
GATE 3

Vertical kernel slice

1つの高価値 feature を geometry、topology、naming、builder、Agent、persistence、negative matrix まで通して完成させる。

Exit: supported / unsupported subset が machine-readable かつ安定
GATE 4

Operational proof

外部 format corpus、trait / non-macOS test、performance budget、fuzz、resource limit、WASM runtime を受入条件にする。

Exit: “works” がコード量ではなく再現可能な証拠になる
